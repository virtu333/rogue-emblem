# Ask about Rogue Dawn mechanics

This is a navigation guide for assistants with browsing or GitHub access answering
player questions about Rogue Dawn (formerly Rogue Emblem / Emblem Rogue). Read the
relevant sources on demand; this document is not a second catalog of balance values.
It covers rules explanations, interactions, strategy, and investigation of reported
behavior. Answering a question does not require changing code or running the game.

## Start here: choose the gameplay revision

- Default to current `main` gameplay. Resolve its commit once and use that revision
  consistently for data, implementation, and tests. State the revision briefly in
  the answer's source note, rather than making the player choose before answering.
- If the player supplies a build, release, tag, or commit, use the matching source.
  [TestFlight notes](testflight-beta.md) may map a build to a source commit. If no
  mapping can be established, explain the general current rule and disclose the
  version uncertainty. The [package version](../package.json) alone is not a unique
  identifier for every TestFlight build.
- If arriving through a PR, read the PR description and open this guide from its
  head branch. A documentation-only PR supplies navigation, not a different gameplay
  release: still use `main` gameplay by default. For a question about a gameplay PR,
  use its head commit and clearly label the answer as proposed/unmerged behavior.
- Relative links below work on GitHub from a branch or commit. When using them to
  investigate a different gameplay revision, substitute that revision in the URL or
  pass it as the GitHub API `ref`; do not silently mix branch files with `main` files.
- An unmerged or closed PR can be shared as an entry point while accessible. Its
  branch link can disappear if the branch is deleted; a guide link pinned to the
  documentation commit is a more durable reference. Pinning the guide does not pin
  the gameplay revision unless the player asks for that revision.

## Evidence and answer procedure

1. Classify the question: a general rule, a named entity, an interaction, a specific
   observed outcome, strategy, or a possible bug. Use the topic map below to start
   with the smallest relevant set of files. Search exact names and IDs for entities.
2. Read explanatory text and canonical data, then the executable path that applies
   the rule. Follow imports and callers when the starting file only constructs an
   effect or supplies a helper. Runtime behavior is established by code **and** its
   configured data, not by a description field alone.
3. For interactions, inspect each effect and how the effects are combined: trigger
   conditions, initiator/defender role, range, terrain, current HP, addition versus
   replacement, caps, rounding, activation chance, duration, and execution order.
   Distinguish per-strike, per-combat, per-phase, per-turn, per-battle, per-act, and
   per-run effects. Creation-time bonuses may differ from ongoing modifiers.
4. For an outcome shown on screen, trace presentation as well as resolution. Base
   helpers and roster values may omit contextual modifiers. A forecast can display
   a probability or planned strike count without promising the eventual result.
5. Read relevant tests to corroborate edge cases. Fixtures, mocked callbacks, and
   harness defaults are not canonical starting stats or proof of live UI behavior.
   Do not claim tests passed unless they were actually run.
6. Give the direct answer first, then explain the condition or calculation in player
   language. Include a numerical example when useful, labeled as hypothetical if
   it is not the player's actual state. Link the few sources that establish the
   answer, preferably at the resolved gameplay commit and relevant lines/symbols.

### Which sources win?

| Source | How to use it |
| --- | --- |
| Current executable code and canonical `data/` at the chosen revision | Establish implemented rules together. Follow actual callers and application paths. |
| Help, compendium, and descriptions | Start with the player explanation; verify exceptions and interactions in code. |
| Tests at the same revision | Corroborate an asserted case; inspect setup and mocked behavior. |
| Specs, GDD, design logs, PR discussions, archived docs | Explain intent or history. Check implementation before treating a claim as shipped. |
| README highlights and old release notes | Navigation and release context; counts and summaries can lag current gameplay. |

`data/*.json` is canonical content. `public/data/` is its generated runtime mirror.
[referenceViewer.json](../data/referenceViewer.json) and
[mechanicsHelp.js](../src/data/generated/mechanicsHelp.js) are generated by
[buildReferenceContent.js](../tools/buildReferenceContent.js); trace values back to
their inputs rather than treating generated copies as independent evidence.
If reference text and executable behavior disagree, say so: describe what the code
does and separately identify any apparent documentation mismatch or bug. Do not
assume Fire Emblem rules apply just because names or mechanics look familiar.

## Worked investigation patterns

### "Why does a heavy sword stop me doubling?"

Read `calculateEffectiveWeight` and `calculateEffectiveSpeed`, then inspect the
doubling branches of `getCombatForecast` and `resolveCombat`. Check skills,
accessories, weapon stat bonuses, and active arts before claiming a specific result.

As a **hypothetical base-rule example**, with SPD 12, STR 10, sword weight 7,
no other bonuses, and an ordinary sword, the weight penalty is
`max(7 - floor(10 / 5), 0) = 5`, giving AS 7. An opponent at AS 4 is only three
points slower, below the base five-point follow-up threshold. Verify the current
formula and threshold in the chosen revision before reusing this example. Brave
strikes, art multi-hits, and contextual follow-up exceptions need separate checks.

### "Do two bonuses stack?"

Find both named entries and their effect keys. Locate where each enters combat
mods or stored unit stats, then inspect the merge and the final consumer. Report
whether they add, replace, cap, or apply at different times, with the triggering
conditions. A generic merge helper is not enough if a caller combines those fields
separately. Avoid extrapolating a universal stacking rule from one pair of effects.

### "Can Deathburst kill me?"

Read the `deathburst` entry, `getOnDeathAffixes`, and its actual death-handling
caller in `BattleScene`. Inspect affected factions, range, HP floor, removal, and
chained deaths. Do not infer lethality from the amount alone or assume that every
post-combat/death effect flows through `PostCombatEffects`.

### "Why did the forecast show two attacks but I only saw one?"

Read forecast construction, `forecastDisplay`, and strike scheduling/early exit in
`resolveCombat`, then the relevant playback caller if necessary. Distinguish a
planned count from strikes actually reached after a death, and probabilistic procs
from guaranteed attacks. Request the screenshot, combatants, or recorded sequence
only if the missing state prevents identifying the actual cause.

## Specific state, strategy, bugs, and spoilers

- For an actual combat, relevant state can include both units' class, current/max
  HP, STR/MAG/SKL/SPD/DEF/RES/LCK, weapon stats and range, rank, active skills,
  accessories, traits, arts, affixes, temporary conditions, terrain, distance,
  nearby aura sources, initiator, turn/phase, and difficulty. Ask only for the
  missing subset needed to resolve the question. Base catalog stats are not the
  player's leveled, forged, upgraded, or buffed unit.
- For strategy, make the objective explicit (survival, reliable kill, resource
  conservation, faster clear, etc.). Separate guaranteed rules from probabilistic
  outcomes and tactical recommendations. Explain useful tradeoffs; source access
  does not prove an optimal build or move.
- For a possible bug, distinguish the report, the intended rule, and the observed
  implementation. Describe a plausible cause as a hypothesis unless code tracing
  or reproduction establishes it. Never claim to have reproduced a report merely
  because a test or historical PR resembles it.
- Avoid unsolicited story, boss, recruitment, and undiscovered Deed/Oath spoilers.
  Match the scope of the question; asking explicitly about a named hidden mechanic
  permits answering that mechanic. Public source access does not reveal what the
  player has unlocked. [CompendiumOverlay](../src/ui/CompendiumOverlay.js) and its
  knowledge providers show the in-game disclosure policy, not the player's state.

## Maintaining and reviewing this guide

Keep routes and symbols current when systems move. Link to canonical sources
rather than copying catalog values or volatile counts. Add a route when a new
mechanic creates a meaningful new investigation path; do not list every entity.
README and AGENTS should remain short entry points.

Before changing or sharing the guide, check that file links and named symbols exist
at the relevant revision, then try representative questions using the linked code:

| Review question | Evidence the answer should establish |
| --- | --- |
| Why can a heavier weapon stop doubling? | Weight-adjusted AS and contextual follow-up exceptions |
| Is Hit rating the actual success probability? | Roll distribution and display conversion |
| Does a named skill stack with a named accessory? | Both effect definitions and their combination/application |
| Can Deathburst kill an adjacent ally? | Actual on-death application, target selection, and HP floor |
| Why did an HP accessory behave differently after healing? | Equip/unequip changes and debt settlement timing |
| How do Warp and Rescue differ? | Target and destination rules, range, and passability |
| What does this difficulty change? | Current configured mode, not old README names or counts |
| Why can't you explain this battle from my unit's name alone? | Missing runtime state rather than invented catalog defaults |

This initial feature is documentation only. It needs no bundled model, inference
backend, embeddings, or in-game chat. Future in-game retrieval can reuse this source
map and review questions while supplying actual game state programmatically.
