# Rogue Dawn — Claude Code Guide

## Project Overview
Rogue Dawn (formerly "Emblem Rogue" / "Rogue Emblem") is a browser-based tactical RPG combining Fire Emblem grid combat with roguelike run structure. Built with Phaser.js (HTML5 Canvas), SNES-inspired pixel art, all game data driven by JSON.

**Name:** the player-facing name lives in `src/utils/gameIdentity.js` (`GAME_TITLE`); `tests/GameIdentity.test.js` holds index.html, the web manifest, Capacitor and Info.plist to it. Internal identifiers keep the old spelling on purpose and must not be renamed: `emblem_rogue_*` storage keys, `__emblemRogue*` window globals, the `@emblem-rogue.local` auth email domain, the iOS bundle ID `com.davechen.emblemrogue`, the npm package name, the repo and the Netlify site.

**Full GDD:** `docs/emblem_rogue_gdd.docx`
**Class/Weapon Data:** `docs/emblem_rogue_class_data.xlsx` (already parsed into `data/*.json`)
**Roadmap:** `ROADMAP.md` (long-term vision + architecture notes + actionable implementation waves)
**Mobile Controls:** `docs/mobile-controls-spec.md` (HTML overlay, landscape, context-sensitive buttons)
**Portrait mode:** `docs/portrait-battles.md` (upright play on phones, on by default; Settings → Portrait mode or `?portrait=0` turns it off; iPad app stays landscape. `html.portrait-ui` keys every portrait layout, and every such rule sits inside `@media (orientation: portrait)` (`tests/PortraitCssGating.test.js`); battles turn the board by a Grid presentation transform and orientation switches re-open from the battle checkpoint; upright browser specs live in the `portrait` e2e lane and share `tests/e2e/portraitHelpers.js`)
**iOS Port:** `docs/ios-port-spec.md` (Capacitor wrapper, deferred until mobile web stable)
**Android app:** `docs/android-development.md` (Capacitor `android/`, same app ID; system Back is the input bus's Cancel (`utils/androidBackButton.js`), tablets locked landscape in `MainActivity`; Google Play builds and uploads from `.github/workflows/play.yml`)

## Tech Stack
- **Engine:** Phaser.js 3 (HTML5 Canvas)
- **Language:** JavaScript (ES modules)
- **Data:** JSON files in `data/` (source of truth) synced to `public/data/` (runtime). Edit `data/*.json` then run `npm run sync-data` (or let `npm run build` auto-sync)
- **Build:** Vite for dev server and bundling
- **Hosting:** Netlify (static CDN) — https://emblem-rogue.netlify.app
- **Auth:** Supabase Auth (username/password, email confirmation disabled)
- **Cloud DB:** Supabase Postgres — 3 tables (`run_saves`, `meta_progression`, `user_settings`) with RLS per user
- **Persistence:** localStorage primary with 3 independent save slots (`emblem_rogue_slot_{1-3}_meta/run`). Supabase cloud backup (push on save, fetch on login) with per-table write serialization and meta `savedAt` freshness guard. Offline play degrades gracefully. Old single-save data auto-migrates to slot 1. Anti-refresh: battles persist a suspend checkpoint (`battleInProgress` flag; `BattleSuspendController`) after every action with the live and resumed RNG streams aligned (a fresh battle of a standard run opens its stream on its own seed per run and node, `BattleScout.deriveBattleStreamSeed`, never the stream an earlier battle used; the prologue run keeps its pinned seed, `data/prologue.json` `seed`, its chapters being tuned on that stream: `BattleScout.openingBattleStreamSeed` is the one rule `BattleScene.installBattleRng` follows; a `?devScene=` review route pins the run seed's stream too, through the registry's `PINNED_BATTLE_STREAM_KEY`, because its fixtures and browser specs are tuned on it) — any exit (refresh/crash/Save & Exit) offers Resume Battle (exact restore) or Continue from Map (sanctioned full revert with entry-time Vision refund; the RNG refund is inert for a fresh battle, which re-derives its seed from the node, so a save written before the per-node stream rerolls once) on continue, so refresh restores resolved actions from the latest durable checkpoint. If device storage refuses writes, Retry blocks the next action boundary; choosing Keep playing accepts that a close or crash loses changes since the last durable checkpoint (a step that can be refused is refused instead: the formation's Roster leaves the battle only if that save lands, else the run stays in the battle and Retry / Back to formation is offered, `ui/FormationRoster.js`). This storage-refusal case is the bounded exception to the anti-refresh guarantee.
- **Run-format guard:** `engine/RunFormat.js` (docs/specs/large-maps/04-set-pieces.md §12.1, §12.2). A run holding a mechanic an older client would misplay (a capability: `encounters`, `parModel`, `objectives`, `gateTerrain`, `bossKit`, `arena`, assembled `setPiece`) is marked by `toJSON` (`requiresClient`, `requiresCapabilities`, with a ratchet), refused by `loadRun` / `fromJSON` on a client without it (the save left untouched; the slot card says "Update needed"), and kept off the cloud while `CloudSync.CLOUD_SAFE_RUN_FORMAT` is 1. A writer's PR adds its id to `CLIENT_CAPABILITIES` and every new saved key to `RUN_FORMAT_FIELDS` (`tests/harness/RunFormatRegistry.test.js` fails on an unlisted key; its census walks the route map and its nodes too, with every writer's data switch on: the Descent's). This build plays the Descent's four: `descent` (`nodeMap.descent`, a node's Descent stamps, a route boss's `bossName`/`bossRole`; `RunManager._buildActNodeMap` raises the run's floor as it builds the route, so every save from route entry on is refused by a client without it, whatever happens after), `rite` (`run.rite`, the `rite*` params, a config's `riteMods`/`entitySplashCount`), `vigil` (a config's `vigil`, a checkpoint's `vigilState`), `defeatObjective` (BattleObjectives' version-1 model of `defeat` primaries on params or a config, any act; RunFormat reads it by its own keys, so any other written model stays `objectives`). A Descent run is local-only while `CLOUD_SAFE_RUN_FORMAT` is 1; it turns so at route entry, so its first local-only push (once a session per slot and run, retried after a failure) and a login that finds it (every time, even after this session retired it: another device may have saved the copy back) retire the cloud row holding the same run's older copy (same `runRecordId`; another run's row, or one with no id, is kept for the login's conflict choice), and the login merge never lets that copy replace it (`CloudSync.shouldPreferLocalRun`; `tests/CloudSyncFormatLocal.test.js`). Tests: `tests/RunFormatDescent.test.js`, `tests/RunFormatDescentOlderClient.test.js`.
- **Art Pipeline:** Google Imagen 4 API for AI-generated pixel art (see Art Pipeline section)

### Scene Flow
Auth/offline gate (main.js) → Boot → Title → SlotPicker → HomeBase → DifficultySelect → BlessingSelect → NodeMap ↔ Battle → RunComplete → Title. Dev routing: `?qaStep=` or `?devScene=` query params skip to specific scenes.

### The Prologue (the first thread)
`docs/specs/prologue-chapter.md`; the story is complete (P1 → P2 → the fork → P3 → the Old Watchtower → P4 → the ending → Home Base). The prologue is a run that never counts (`RunManager.mode: 'standard' | 'prologue'`, serialized; old saves are standard): `data/prologue.json` (authored chapters P1 "Banner at Dawn", P2 "Old Hands" and P3 "The Seer on the Road" with their maps, kits, `villageTile`, `loot`, `showPar`, P3's green `npc` Sera, and P4 "The Quarry Gate" (four units for three spawns: a `deploy` rule with its note, `formation` spares, `rosterEquip` for the replay's Gaspar, Captain Varro on the throne, seize, par); the `route` with the row-2 fork, Harrow's Market (authored `stock`, no Restock) | Harrow's Chapel (blessings greyed), node `preview`s, row 4's Old Watchtower (a Ruins node with its own `stock` and arrival `lines`, Sera's vision), P4's node `bossLine`; `joins` (`afterChapter`, `atNode`: Tamsin joins unarmed at either fork node, her bow granted there if the army lacks one); `boss` (Varro: in no act pool; the boss card reads his epithet from here); `ending` (`music`, `scenes` of lines, ceremony cues, a shake, veils, PROLOGUE COMPLETE (`card`) on a `won`-only scene, the title card)) → `engine/Prologue.js` (`buildPrologueBattleConfig`, `buildPrologueNodeMap`, `buildPrologueRoster`, `buildPrologueNpcUnit` (the one NPC builder BattleScene and HeadlessBattle share), `buildPrologueShopStock`, `buildPrologueLootChoices`, `prologueBeatsFor`, `prologueProtectedNames`; validated by `npm run validate:data`) → `RunManager.startPrologue` (Edric alone, the literal route with every chapter pre-locked in `battleConfigsByNodeId`, Vision 0, Eclipse off, Act 1 on Normal, no meta effects; `joins.afterChapter` commit in `completeBattle`; `arriveAtPrologueNode` for arrival joins (`ui/PrologueArrival.js`: saved, then the recruit card); `grantPrologueVision` once per run, reverted with the battle; `restartPrologueBattle` reverts to the chapter's entry even past a fatal checkpoint; `failRun` refuses) → `BattleScene` + `ui/PrologueController.js` (coach, gates, highlights, notes, tips, lines, Talk/heal/rewind beats, the protected-unit intercept, victory records; every hook returns a task that settles once its notes and lines are read and the scene awaits it through `safeBattlePresentation` at the site the beat belongs to (`removeUnit` for a fall, the Seize command before the victory flow), so a blocking sequence owns its interval of the simulation, and the player turn-start pipeline awaits `idle()` before it reads the battle state; its teaching state rides the suspend checkpoint via `snapshot`/`onResume` (version 2: spent beats, the gate, the ledgers, the damage ledger and the unread notes/lines as `pending` records, replayed on resume; a hint is marked read only when its note is acknowledged), so a resume never replays `battleStart`; the hook contract and what survives suspend are the tables in spec §9). Density (spec §2 "Core and reinforcement"): each chapter's small core is its blocking `note`s (P1 2, P2 2, P3 3, P4 2 with the deploy note; `prologueNoteBudget`); everything else is a `tip`, never awaited, never pending: a `GuidanceNote` beside the map (`ui/PrologueTip.js`) or, raised by a forecast, one line in its notes (`prepareForecast` before the render; read only on Confirm/Cancel). A tip marks its hints only once read, so an unread lesson is still taught at its Act 1 point of use (`tests/PrologueDensity.test.js`). Settings → Guidance thins it for a player who knows the genre (`Guidance.prologueGuidanceAllows`, read live): Light drops the tips, Off the blocking notes (deploy note included) and P1's guided steps too; the story, the coach's goal line (Hide folds it to a Guide chip) and the exits stay. P3's rout requires Sera (`requiredRecruits`, validated; `engine/RoutObjective.js` `isRoutComplete` is the one rout predicate `BattleScene.checkBattleEnd` and the harness read: the last Soldier's fall leaves the battle playable until the Talk, which then checks the end; a standard run requires nobody). A practised lesson is marked only when the skill was shown: `combatResolved` carries the committed `distance` and `damagedBy` (P2's chip-then-finish needs Gaspar's damage on that foe, P3's range-two a strike from 2 tiles), `deployed` is raised from the deploy screen's confirmation (`scene._deployConfirmation`), and the roster lesson's Withdraw/Equip read the army's state after the action. The row-2 roster lesson (core Withdraw → Equip, then Trade and Store offered as more; once, skippable, never blocks travel) is `engine/PrologueRosterLesson.js` (pure ledger on `RunManager.prologueRosterLesson`, `more: null | accepted | declined`) + `ui/PrologueRosterCoach.js` (the strip in `MobileRosterSheet`, which every browser Roster uses); travelling on from the fork with Tamsin unarmed asks Open Roster / Continue anyway, once per attempt, never a gate (`engine/PrologueDeparture.js`, `ui/PrologueDepartureWarning.js`, in `NodeMapScene.onNodeClick`) → `ui/PrologueEnding.js` (the ending's scenes with existing tools: `music_explore_deep`, the `sealed` / `eclipse` / `rewind` cues, PROLOGUE COMPLETE after a win (never after a skip, `prologueWasWon`), the Hollow Sun veil, THE THREAD BREAKS card (never the game over's words); lines adapt to a skip via `endingLinesFor`; then the handoff (`ui/PrologueHandoff.js`: what ends a run, fallen allies, what starts over, what stays, Vision; once), `meta.completePrologue` with the grant paid once, the run save cleared, Home Base). Routing is pure: `engine/PrologueRouting.js` (`routeForSlot`, `routeForBeginRun`: a lost prologue run save (state left `in_progress`) gets the offer again at Begin Run; `meta.prologue.state ∈ none | in_progress | skipped | complete`, merged on cloud fetch by `mergePrologueState`), the starts live in `utils/firstRunFastPath.js` (`startPrologueRun`, `skipPrologueToFirstRun`). A fresh slot's New Game (Title and Slot Picker) offers Play the Prologue ("about 30 minutes": a harness estimate for a first-timer, a playtest hypothesis, spec §9) / Skip; a fresh device's title "Prologue · Start here" starts the run; with saves it offers Continue the prologue (an unfinished prologue run), Play the Prologue as a new save (next free slot), then Replay a chapter: a chapter select whose standalone replays set the slot aside (`prologueReplayStash`) and never write it. Copy: coach/note/offer/Home Base text in `src/data/prologueContent.js`, spoken lines in `dialogue.json` `prologue`. Harness: `tests/harness/PrologueP1/P2/P3/P4.test.js` (each chapter starts from the previous one's real end states: `prologueP2Policies.js`, `prologueP3Policies.js`, `prologueP4Policies.js`).

Three predicates in `engine/ScriptedBattle.js`, and every run-layer reader uses one of them, never a mode string or a private flag (`tests/ScriptedBattleSuppression.test.js` drives each reader in both modes): `isScriptedBattle(battleParams)` is the teaching suppression in both the run and a standalone replay (Eclipse, Guidance, contextual hints, deeds, formation (unless the chapter names `formation`: P4), rolled caravans/villages, story beats, commander last words, the first-battle theme); `isStandaloneScriptedBattle(bp, rm)` means no run layer (no suspend/intent writes, no slot); `isPrologueRun(rm)` switches the run layer itself (no cold open or act card on its route map, no Abandon Run, no boss recruit, third lord, Vision grant or advanceAct, no act milestone, the loom header "Prologue · The Quarry Road"). A chapter with `showPar: false` has no par. The chapter never counts: no `runsStarted`, no Vision grant from a chapter; a protected unit's fall restarts the chapter ("Not this thread"), with an unspent Vision charge offered first. Completion keeps the device-wide keys `emblem_rogue_tutorial_completed` / `emblem_rogue_tutorial_lessons` (`ui/prologueLessons.js`, `applyCompletedTutorialHints` for new slots) and, in the run, marks the slot's hints as the notes show; the `.re-tutorial-note` / `mb-tutorial-*` CSS hooks and the `TUTORIAL_HINT` battle state keep their names. The prologue's run save is local-only: `CloudSync.isLocalOnlyRunSave` never pushes a `mode: 'prologue'` run (older clients would load it as a standard run); the slot's meta, including `meta.prologue`, still syncs. Logout's backup says what it could not carry (`backupAllLocalSlots` → `{ ok, localOnly }`), and sign-out asks before discarding an unfinished prologue (Keep playing / Sign out anyway), even after a confirmed backup. The grant's receipt travels with the economy that holds it: the cloud fetch keeps one meta payload whole, so `grantPaid` comes from that payload only (`reconcilePickedPrologue`; a completion only the other copy saw is paid into it once), and the local adopt (`MetaProgressionManager._adoptForeignDiskStateIfNewer`) does the same: a newer copy on disk is adopted with its economy whole (currencies, upgrades, assignments, NG+, paid-run ids), only facts that grow are unioned, and every change goes through `_commit` (adopt first, write once, roll back on a failed write), so a stale tab never brings back spent currency or a refunded tier (`tests/MetaSaveTransactions.test.js`). Browser specs: the `prologue` e2e lane, and `portrait-prologue.spec.js` in the `portrait` lane. Its ordinary-play specs (`prologue-journey-market` / `-chapel`, `prologue-falls`, `prologue-resume`, `prologue-skip`, `portrait-prologue`) never call onVictory, removeUnit, completeBattle or a setter: they play through `tests/e2e/prologueDriver.js` (clicks, taps and keys on the real board, menu, rail and DOM; a planner that reads the board to choose a move; waits on state) and `tests/e2e/prologueJourney.js` (each chapter as a player plays it).

### NG+ (New Game+)

## Data File Gotchas
Read the JSON files directly for full schemas. Non-obvious behaviors:
- **classes.json** — Base classes have `growthRanges` (string "55-70", rolled once at recruitment). Promoted classes have `promotionBonuses`. Some have `learnableSkills: [{ skillId, level }]`.
- **Item names are identity** (saves store whole items; weapon-art gates, siege lookups, icons and fx key on names). Renaming an item goes through `ITEM_RENAMES` + `ITEM_NAMES_REVISION` in `engine/ItemNameMigration.js`, which `RunManager.fromJSON` runs over old saves (`docs/specs/item-names.md`). Weapon names follow the family grammar there; rule tags come from `engine/ItemKeywords.js` (`docs/specs/item-keywords.md`).
- **Compendium discovery** (`engine/CompendiumDiscovery.js`) — the Compendium's Arms, Items and Skills entries read "???" (`ui/compendiumLocked.js`) until a save has met them: offered (an unclaimed reward's choices, a shop's stock), owned (any unit's kit and skills, the convoy, accessories, scrolls) or used against the army (a foe's held weapon, accessory and skills at `BattleScene._runCombatResolution`, a foe's status staff). The manager keeps `itemsSeen` (catalog names: a "+N"/"-N" copy records its base, an imbued one drops its adjective, an `ITEM_RENAMES` old name its new one) and `skillsSeen` (ids) in memory, recorded beside each run save (`NodeMapScene.persistRunSave`, `saveServiceRun`, `BattleScene._persistBattleRunState`). **Saved, they live inside `purchasedUpgrades`** as `__seen_item:<name>` / `__seen_skill:<id>` keys with value 0 (never as fields of their own: a build from before them writes a fixed field list and would drop them, but copies and max-merges `purchasedUpgrades` whole); the in-memory map never holds them (`withoutDiscoveryKeys` on load, `withDiscoveryKeys` on save), and `isFreshMetaPayload` ignores them. Every load unions the keys with the backfill (victory records, skill assignments, the slot's run); the cloud fetch and a stale manager's adopt-merge union both copies. The Compendium reads every slot on the device (`discoveriesAcrossSlots`, a slot kept at logout included), the open meta and the run in play. A weapon's entry lists its own arts (`weaponArtDetailLines`); a legendary art's entry names the weapons that carry it once they are found.
- **Necromancer and Skeleton** (`docs/specs/phase3.md` 3I; `engine/Necromancy.js`, pure, shared by `ui/NecromancyController.js` and the harness's `_processNecromancy` / `_removeUnit`) — two enemy-only classes: the **Necromancer** (promoted from Mage, `Tomes (M)`, carries the enemy-only Steel tome **Gravesong** via classes.json `enemyWeapon`: price 0, in no loot table, validated; a dark class; AI `guard`, never a hold-pack member) and the **Skeleton** (base, Infantry, `Swords/Lances/Bows (P)`, low growths). Both are in `ENEMY_ONLY_CLASS_NAMES` / `DIFFICULTY_GATED_CLASSES`. The Necromancer is in the Act III and Act IV `promoted` pools; `enemyClassEarliestAct` gates it (Dusk and Nightfall `act4`, Black Sun `act3`, First Light never). `MapGenerator` maps a second Necromancer pick to the pool's next class (`mapExtraNecromancer`: no re-roll, no extra draw), and reinforcement templates, ladder waves and arena bouts never take either class (`isNecromancyClass`). **Raising**: at each enemy-phase start, right after `processZombieRevival`, every living Necromancer with fewer than 2 living Skeletons of its own raises one onto `riseTile`'s first free passable neighbour (none if there is none); a Necromancer raises at most `NECROMANCER_RAISE_CAP` (6, `constants.js`) in a battle in all (`_raisedCount` on the Necromancer, kept by `serializeBattleUnit`, so a suspend restores it and a rewind takes it back), then raises no more even with none standing; the Skeleton has not acted, is its Necromancer's XP-effective level less 4 (min 1), and is built on `keyedBattleRandom(battleSeed, 'raise:<necro id>:<turn>:<n>')`, never `Math.random`, so a raise never moves the battle stream and a resume or rewind replays it. `_raisedBy` links it to the Necromancer's `battleEntityId`. **Rewards**, one predicate for every conjured unit (`engine/ConjuredUnits.js` `isConjuredUnit`: raised or summoned; a leaf module, `isRaisedUnit` re-exported by Necromancy): gold 0, XP x0.25 (`conjuredXpMultiplier`), no survival XP (`BattleXp`), no deed record (`isZeroRewardUnit`), never a carrier (`EnemyCarry.isCarrierEligible`); a Skeleton never carries items (a guard comment in `buildRaisedSkeleton` for the Steal step). **Crumbling**: a Necromancer's fall removes its own Skeletons with no killer (`crumbleFor`, in the enemy branch of `removeUnit` / `_removeUnit`, before the battle-end check, so a Rout completes on its fall). The raise banner and effect play only on a tile the player sees. Skeleton XP slice: `tests/sim/NecromancerXp.test.js`.
- **Circle Adept and Hollowed** (Act V "The Descent", `docs/specs/act-v-descent.md` §5, PR 3; no pool fields them: set pieces and the Vigil's circles do, next bullet) — two more enemy-only classes beside the Necromancer pair, in `ENEMY_ONLY_CLASS_NAMES` / `DIFFICULTY_GATED_CLASSES` and every rung's `enemyClassEarliestAct` as `finalBoss` (First Light's table too: a set piece skips First Light's blanket ban on the gated pools but reads this table, so `validateSetPiecesConfig` refuses either in an Act I-IV event set piece on every rung). The **Circle Adept** is promoted from Mage (`Tomes (M)`, MOV 4, a dark class: `DARK_CLASSES`, Endword reaches it; at the same level about a Sage's MAG with Necromancer-grade RES and a Sage's DEF: warded, soft to steel) and carries the enemy-only Steel tome **Greycord** (`enemyWeapon`, price 0, in no loot table, validated like Gravesong; `WEAPON_ICON_REUSE` gives it Gravesong's icon cell, the atlas being full); a set piece slot of one defaults to AI `guard` (`SetPieces.defaultAiMode`). - **terrain.json Ice** — Slides are priced (`engine/IceMovement.js`): stepping onto Ice costs the tile, the first tile slid past it is free, each further tile costs its move cost, and a slide the unit can no longer pay for stops on the ice and ends the move. `Grid.computeMovementRange` (also the harness grid's, never a copy) marks those tiles `slideStop`; `reconstructRangePath` carries the mark on the path's last tile, and `computeEffectivePath` stops a slide early only on a marked path (an A* path always slides to its end). `FogAmbush.pathCostTo` prices slides the same way, so Canto's remaining MOV agrees. A unit another unit's action puts on Ice (Shove, Smite, a weapon-art push or ram) slides too, free, over the same slide: `IceMovement.slideAcrossIce` is the one slide (walking's `resolveIceSlide` and the forced `traceForcedSlide` call it), `ForcedMovement.traceForcedMove` composes a push with it; fliers don't slide, the slide ends on the first non-Ice tile (hazards included) or stops on the last Ice tile at an edge, a unit or ground the move type can't stand on, and a slid tile counts as a tile of the push. A unit moving itself (Pull's puller, art advance/retreat/through/swap, Swap) and teleports don't slide. Previews trace the slide over known units only (`ui/forcedMoveProbes.js`); execution traces the real board, so a hidden unit stops it like a walk's ambush (`docs/specs/utility-abilities.md`). A player's own slide meets the real board the same way (`FogAmbush.fogMoveCut`, which `BattleScene._ambushCut` calls for the walk and for Canto): a hidden unit on a slid tile holds the slide even for a Pass unit (Pass walks through a foe, never slides through one), so the unit rests on the last free ice tile and is ambushed there, and the move ends where it is cut; a hidden unit on the ice entry tile is a normal step for Pass (as a seen occupant is) and the slide starts on the next ice tile, repriced from there, and a step the allowance can no longer pay stops the unit before that unit.

Smite is blocked by bosses, the Entity, Anchored and root; Transfuse never takes the giver below 1 HP and skips a Wounded ally. **Great Sacrifice** (`sacrifice_heal`, scroll) pays `min(10, HP - 1, what the most hurt healable ally in range is missing)` through `damageUnit` (floor 1) and heals every ally within 2 by that much (`healUnit`: a Wounded ally heals nothing and is never counted, so it is only offered when it would do something). **Goddess Dance** (`refresh_adjacent`, the Bard learns it at level 5, no scroll, never lent: `neverBound`) refreshes every cardinal neighbour that has acted and is not a dancer: `findDanceRefreshTargets` is the one rule Dance's own targets read, and `refreshActedAlly` the one refresh (`_movementSpent` stays, as Dance), with a deed and Dance XP per ally. **Blink Strike** (`warp_strike`, scroll) is the one ability that leads into an attack (`ui/WarpStrikeController.js`): destination (a free tile of Blink's diamond the EQUIPPED weapon strikes a seen foe from; a bow user is offered only its range) → foe → the ordinary forecast read from the destination (`AttackFlowController.atWarpDestination`: no weapon to cycle, never an art) → Confirm. Nothing moves until Confirm and Cancel steps back one stage. Confirm re-plans (`planWarpStrike`, against `PlayerKnowledge`), settles the warp in the domain (`settleWarpStrike`) and in the same turn calls `executeCombat(unit, foe, { warpStrike })`, whose first act is the intent checkpoint: it already holds the warped unit and the spent use (`pendingCommittedAction.warpStrike`), so the warp is never a durable state of its own (two writes, as any attack: the intent and the resolved action), the rewind row reads "Before X's Blink Strike on Y", a resume replays it as a Blink Strike, and Canto is never offered. A unit the fog hid on the destination (the real board, not the player's view) fails the warp: the use is spent, the unit stays, the action ends. Shove, Pull and Dance stay hardcoded (no `actionAbility`); Swap is an innate command, not a skill. Shove and Smite are forced moves: a unit pushed onto Ice slides on (see the Ice line above). Spec: `docs/specs/utility-abilities.md`.
- **Pass** (passive, innate to the Trickster beside Darting Blow, a scroll, lendable in Act IV): the unit moves through enemy units and never stops on one. The rule is `Grid.computeMovementRange` / `computePath` with `{ pass: true }` (`passesThrough`: enemy units only, never for an enemy mover, NPC allies still block; a foe's tile is entered and marked `stoppable: false`, as an ally's). Every player-unit movement call passes `PassMovement.movementOptionsFor(unit)` (read through `effectiveSkills`, so a lent Pass works exactly as a known one); previews read `buildOccupiedSet(u, { seenOnly: true })`; an occupied tile still ends an ice slide; at execution `FogAmbush.fogMoveCut`'s `passes` probe lets a hidden foe on a walked tile go unnoticed, while one on the LAST tile, or on a slid tile (it holds the slide, see the Ice line), still cuts the move. The unit a committed move ran into is shown for the rest of that player phase even past the mover's vision (`Grid.revealContact` in `_resolveAmbush`; `contacts` ride the fog in the checkpoint and the rewind, `ui/fogState.js`; cleared as the enemy phase starts). The AI's code (`AIController`, `enemyThreatTiles`) never asks for it. `HeadlessGrid` shares `computePath` (no copy), so the harness moves a Pass unit through foes.
- **The Entity's kit** (anti-kiting; `engine/EntityKitConfig.js` (leaf: shape, validation, summary lines) and `engine/EntityKit.js` (rules); difficulty.json `entityKit` per rung `{ limbs: null | { maxAlive, maxSprouted, woundPercent }, undertow }`, optional (absent = off); First Light and Dusk none, Nightfall limbs 2 / 8 / 4%, Black Sun limbs 4 / 12 / 4% + undertow). `RunManager.getBattleParams` carries it on Act V params (inert), `MapGenerator` locks it into the config only when a spawn is the Entity, so a battle plays the kit its map was made with (run-format capability `entityKit`: a config's `entityKit`, a checkpoint's `entityKitState`). **Grasping Limbs**: each tile the army struck the Entity from in a player phase is noted (`PostCombatEffects` → `entityKitAfterCombat`, before any move); at the next enemy-phase start, after the Vigil's step, `limbPhaseStep` raises a Grasping Limb (boss-tier class, MOV 0, Coil reach 1, level 20) on each noted free tile, else the free tile nearest the body, up to `maxAlive` standing and `maxSprouted` a battle, each on `keyedBattleRandom(seed, 'limb:<turn>:<n>')` (never `Math.random`); `_summonedBy: 'entity:limb'` makes it conjured (gold 0, XP x0.5, no carry, never copied: `isNeverCopiedClass`), immovable (`displacementBlockReason` 'entity'). The Entity strikes anyone beside a living limb too (`EntitySystem.canEntityStrike`, read by the AI; Danger adds a visible limb's neighbours). A limb the army cuts takes `woundPercent` of the Entity's max HP (floor 1, `severLimb`, through `damageUnit`); the Entity's fall withers every limb. **Undertow** (Black Sun): an Entity counter that lands drags its attacker one tile toward the nearest body tile (`undertowPlan`, `traceForcedMove`, ice slides) and roots it one turn (`recoveryChance` 0: no Canto, Swap, Shove or Pull). State `entityKitState = { strikes, sprouted, severed, lastProcessedTurn }` rides `captureBattleWorldState`. Scene: `ui/EntityLimbController.js`; harness: `tests/harness/headlessConjuring.js` (with the Necromancer's and the Vigil's steps). Tests: `tests/EntityKit.test.js`.
- **The Merchant Caravan is walked through** — every player unit (with or without Pass) crosses the merchant's tile as an ally's and never stops on it; foes and every other NPC stay blocked. `Grid.walksThrough` is the one occupancy rule (own side, the merchant for a player mover, Pass foes), read by `computeMovementRange` and `computePath`; unit-position maps mark the merchant through `PlayerKnowledge.unitPositionEntry` (`isCaravan`), which the scene's previews and the harness both use, and the AI builds its own map without it. A merchant the fog hides is walked through too (`PassMovement.passesHiddenUnit`), but on the last tile or a slid tile it cuts the move as any hidden unit does. Forced moves (Swap, Blink, Shove, Pull, Smite, art pushes) still treat it as blocking (`tests/CaravanPassable.test.js`).
- **Skill loadout** — `unit.skills` is the equipped list (all battle reads), counted in two pools by `engine/SkillSlots.js`: up to `MAX_SKILLS` (5) skills and, apart from them, up to `MAX_ABILITIES` (3) abilities (`trigger: "action"` in skills.json: Shove, Pull, Dance, Steal, Blink, Blink Strike...; read the kind with `slotKindOf` / `slotsFullFor`, never `skills.length`); `unit.benchedSkills` holds known skills set aside. A player unit that learns with its kind's slots full keeps the skill benched (`learnSkill` returns `benched: true`, reason still `at_cap`), never loses it; enemies never bench. A swap makes room only with one of the same kind (`swapCandidatesFor`); a save holding more abilities than slots benches the overflow once on load (`settleSlotOverflow`, locked skills kept first), on the roster and the fallen and on every copy a suspended battle keeps (`engine/SavedBattleSlots.js` in `RunManager.fromJSON`: the checkpoint's army groups and Talk records, its Vision anchors and each timeline destination, a patch re-encoded against its settled keyframe by `BattleTimeline.reviseBattleTimelineStates`; only the loadout lists move, no stream, item or position), so Resume Battle, a Vision rewind and Continue from Map hand back one loadout (`tests/SavedBattleSlots.test.js`, on a real pre-split save, `tests/fixtures/saves/`). Swaps, lock rules (lord and class skills can't be benched) and the bench notice (`benchedUnseen`) live in `engine/SkillLoadout.js`. Check "knows a skill" with `knowsSkill`, not `skills.includes`.
- **Roster Discard** — `rosterItemAction(run, unit, item, 'discard')` (`engine/RosterInventory.js`, with `rosterItemBlock` / `rosterItemWarnings`) throws a bag weapon, staff or consumable, or a convoy weapon or consumable, away for good: no convoy, no gold, and an equipped weapon leaves through `removeFromInventory` as Store does (`leaves_unarmed` is warned the same). Destroying needs an unambiguous instance and place: the request names the live object and where it is (`where`: `'bag'` | `'convoy'`, the sheet always passes it) and only that container is read, by object identity alone, so a snapshot or clone (`getConvoyItems()` hands out clones), a duplicate uid, an equal copy or a stale reference is "Item is no longer here." and nothing changes (no uid or JSON fallback, and a stale bag request never reaches a convoy copy); `rosterItemBlock`, `rosterItemWarnings` and the action share `locateDiscardable`; accessories and team scrolls have no capacity to free and are left out. It is blocked for a lord's personal weapon (`signatureOf`: nothing hands it back), in the prologue run, and while `battleInProgress`. The roster sheet (`MobileRosterSheet`, which every browser Roster uses) always confirms first (`ChoicePicker` confirmation naming the item) and saves through `persistNow`; the point is an owed contract reward (`run.contractOwed`) that needs a weapon slot while the party is held at a node with no shop (`tests/RosterDiscardContract.test.js`, `roster-discard*.spec.js`).

## Core Formulas (from GDD Section 3.3)
```
Physical Damage = (STR + Weapon Might) - enemy DEF
Magical Damage  = (MAG + Weapon Might) - enemy RES
Hit Rate        = Weapon Hit + (SKL × 2) + LCK - Enemy Avoid
Avoid           = (SPD × 2) + LCK + Terrain Bonus
Critical Rate   = SKL / 2 + Weapon Crit + Skill Bonuses - Enemy LCK
Critical Damage = 3× normal damage
Attack Speed    = SPD - max(0, Weapon Weight - floor(STR / 5))   (+ weapon/skill SPD bonuses; staves: SPD)
Double Attack   = attacker Attack Speed >= defender Attack Speed + 5
```
Doubling reads attack speed, never raw SPD: `calculateEffectiveSpeed` / `canDouble` in `Combat.js` (threshold `DOUBLE_ATTACK_SPD_THRESHOLD`; the Pursuit Ring lowers it, `preventEnemyDouble` effects block the foe's double, an active weapon art gives up its follow-up, and Quick Riposte forces a defender's double). Sims should read `getCombatForecast(...).attacker.doubles` rather than recompute it.

### Weapon Triangle
Swords → Axes → Lances → Swords: +10 Hit, +1 Damage (advantage) / -10 Hit, -1 Damage (disadvantage). Mastery rank: +15/+2 advantage, -5/-1 disadvantage. Magic and Bows are outside the triangle.

## Music (composed in code)
All music is original: 64 loop scores in `tools/music/scores/` and 31 ceremony cues (stingers) in `tools/music/stingers/`, rendered by `tools/music/engine/` (sampler + mixer) to `assets/audio/music/` and `assets/audio/stingers/`. Read `tools/music/SCORE.md` (leitmotifs, the Entity's finale, cue list, boss cards and enrage layers, device budget) and `tools/music/README.md` (setup, build, lint/analyze/pitchcheck tools).
- **Rebuild:** `python3 tools/music/build.py <score>` (or `--all`; `--stingers [names]` for cues), then `npm run sync-assets`. The build regenerates `src/utils/musicLoops.js` (loop points + each track's `tonic`) and `src/utils/musicStingers.js`, so never hand-edit them. A form check refuses any score with a bar where nothing sounds (declare intended silence in `score.silent_ok`).
- **The palette:** `tools/music/engine/palette.py` picks each instrument's library at render time. The game ships `HOUSE` (the sound lab's blind-A/B verdicts): Sonatina Symphonic Orchestra 4 for string sections, solo violin (the performer's `clean` style), oboe, celesta, choir and oohs; Virtual Playing Orchestra 3 for horns/trumpets/trombones; the legacy registry (VSCO 2 CE, GeneralUser GS) for the rest. A score may change one for itself (`s.palette`). Any other `--palette` is an audition and never writes game assets. Those licences need credit: the help overlay's Meta › Music Credits page and `docs/music-credits.md` (the soundtrack is CC BY-SA 4.0; `tests/MusicCredits.test.js` holds the credit to the palette). `bash tools/music/fetch_libraries.sh` fetches every library; VPO3 comes from the unofficial studiorack SFZ mirror (no version, other branches), so its clone is pinned to `VPO3_COMMIT` (a full SHA, credited as an unofficial mirror in both credit pages and held by `tests/MusicCredits.test.js`).
- **Seamless loops:** each file is an intro plus a loop region. `AudioManager` plays it through `LoopedMusic` (Web Audio `loopStart`/`loopEnd`) and falls back to a whole-file loop without Web Audio. A layer that can't share the primary's timeline (stale cache) is dropped, never mis-looped.
- **Entering a battle:** the route map hands its track to the battle (`audio.handOffMusic(this, 'Battle')`) instead of stopping it: it bridges the deploy screen and the battle track's fetch/decode (seconds on a phone), then crossfades into it; a battle track that fails to load takes the bridge down with it (`tests/MusicHandoff.test.js`, `battle-entry-music.spec.js`).
- **Starting a track:** `AudioManager.playMusic` treats audio as locked only while Phaser says so and the context is not running (a tap on a DOM surface resumes the context through `audioRecovery` but never reaches Phaser's body listeners; the context's `statechange` tells Phaser, whose next step emits `unlocked`); while locked it still fetches and decodes the track and its start layers, so the first gesture only starts it. A track's start layers (its own adaptive layers, any additive `layerGains` layer) load beside the primary; any other extra (a boss's enrage layer) joins the running timeline after the start (`_restoreMissingLayer(..., { join: true })`, which leaves the one retry per voice). The Entity's finale and hum are preloaded once its theme plays. The deferred-asset warm-up starts at the title; one handed back when its scene shuts down early is picked up by the route map, Home Base or a battle (3 s after its music), which never start one of their own (`resumeOnly`), so a dev route that skips the title loads nothing behind its page. Tests: `tests/MusicStartLatency.test.js`, `tests/AssetWarmup.test.js`.
- **Adaptive battles:** field battle themes ship as `<key>` + `<key>_calm` on one timeline (`MUSIC_LAYERS`). `BattleMusicController` + `engine/MusicIntensity.js` crossfade calm↔full on combat and threat; `audio.setMusicIntensity()` is the API.
- **Which battle theme:** `engine/BattleMusicSelection.js` (pure) picks a non-boss battle's track from `battleMusicContext(...)`: the Descent (a Vigil map, then any Act V battle: `MUSIC.descent`) → escape → eclipsed / village under attack / recruit rescue / elite, each act its own company (`MUSIC.battleSituation`; an entry is a key, a pool, or a table by act) → the map's biome (`MUSIC.battleBiome`) → a caravan, a bandit village, fog of war → the act pool (`MUSIC.battle`). Escape (`MUSIC.escape`), place and situation entries are each a key, a pool, or a table by act: escapes, rescues, castles and fog have two themes each, split by act (SCORE.md, "Which battle theme plays"). Castles, caravans, bandit villages and fog take only a share of their battles (`THEME_SHARE`). Picks are hashed from the run seed (a resumed battle keeps its track); the act pool, and any pool, is walked per run by node row, so a path never repeats a theme until the pool is spent, and every run opens on Ember Dusk. A new place or situation theme is a score plus one table entry; `MusicLibrary.test.js` checks every one is adaptive and every biome key is a real template biome.
- **Act V themes (the Descent, docs/specs/act-v-descent.md §8):** `battle_descent` ("Ember Dusk, Below": the Stair, the Column and the Landing) and `battle_vigil` ("Through the Floor": the Vigil's mini-boss, no boss card) are adaptive scores registered as `MUSIC.descent.battle` / `.vigil` with their calm mixes in `MUSIC_LAYERS`, and the keyed stinger `voice_silenced` (a Voice falls) is in `MUSIC_STINGERS`. `BattleMusicSelection` picks them ahead of every other rule for a non-boss battle: a map carrying `vigil` plays `.vigil`, any other `finalBoss` battle `.battle` (`battleMusicContext` `isVigil` / `isDescent`; bosses keep their themes); `VigilController` plays the cue for a seen Voice's fall; `MusicLibrary.test.js` holds both adaptive, within the other battle themes' loop lengths, and the cue keyed in their tonics (D and G, both keys the music already uses, so no existing stinger needed a new key).
- **Boss enrage:** each boss theme ships `<theme>_enrage_<boss>` (same timeline, `getBossEnrageLayer`); `BattleMusicController.onBossEnrage()` crossfades to it when turn pressure enrages the boss (`setMusicIntensity('enrage')`).
- **Entity finale (`ENTITY_FINALE`):** the Entity has no enrage layer. Its first wound (`onCombatResolved`, or turn-pressure enrage first) cuts its theme, leaves 2 s of silence, plays the `entity_answer` hinge cue and starts `music_boss_entity_finale` on the cue's `handoff` downbeat (`playMusic(..., { startAt })`, sample-aligned). The `_hum` stem is an additive layer (`layerGains`) whose level follows the Entity's HP (`audio.setMusicLayerGain`). A resumed battle with a wounded Entity opens on the finale. On the finale's downbeat the army answers, one line every two bars (`onFinale` → `BattleBeatsController.entityRally`, composed by `engine/FinaleRally.js`), each as a portrait card (`ui/EntityRallyController.js` + `ui/RallyCard.js` on a map `CeremonyLayer` at `DOM_UI_DEPTHS.RALLY`; the timetable, the card's text and its edge are pure in `ui/rallyCardModel.js`): the speaker's face (`unitPortrait`, slot `rc-face`), name, class, line, a `1 / 5` count and a Skip button, docked on the board's bottom or top edge (whichever covers fewer units; a selected unit's canvas menu counts for more), the speaker's tile marked with the locator's brackets. It holds until the next beat, the last card fades, a card ends when its speaker falls or the battle does, a fallen speaker's line is still left unsaid, and reduced motion cuts instead of fading. It never pauses the battle, takes no input scope and no overlay-stack entry, and is click-through but for Skip (whose presses never reach the board); Skip (or an explicit Cancel: Esc, the input bus's Cancel (the pad's B, Android Back), the phone's Back and the desktop's [X] Cancel, each passing `requestCancel({ cancelAction: true })`) drops every line still to come and every timer for the battle, and Cancel reaches the card only when `BattleScene.requestCancel` finds nothing else to close (`canRequestCancel({ allowPause: false })`: a forecast, selection, menu, panel or overlay keeps its Back; at idle the card takes the press before Pause). `requestCancel` also serves inputs that are not a Cancel and never touch the card: a right-click (which then inspects), a tap off the map, the phone's Menu and the pad's Start (both open Pause, the rally carrying on under it). A host with no DOM falls back to the floating line over the speaker. A resumed battle never rallies (`_rallied`, as before). Browser spec: `tests/e2e/entity-rally.spec.js` (`presentation` lane).
- **Stingers:** `audio.playStinger(name, { fallbackSfx, duck, waitMs })` plays a cue in the key of the current track (keyed cues exist per tonic) and ducks the music; `stopStingers()` fades them. Ceremonies call them through `src/ui/ceremonyMusic.js`; boss cards map in `BOSS_CARD_CUES` (the Entity: silence).
- **The iOS app's music:** the TestFlight workflow re-encodes every music track at LAME V6 (`tools/ios/compactMusic.mjs`, about a quarter smaller, checked sample-for-sample against the original's length) so the app stays under Apple's 200 MB cellular download limit; the web game keeps the build's V4.
- **Adding a cue:** write a score (or stinger), build it, add the key to `musicConfig.js`. `tests/MusicLibrary.test.js` fails on missing files, orphans, bad loop points, a boss without an enrage layer (the Entity excepted) or a keyed stinger missing a key.

## Future Roadmap
See `ROADMAP.md` for all planned features. Key architectural constraints:
- **Don't hardcode Act 1 assumptions.** Enemy pools, loot tables, and map generation must be parameterized by Act.
- **Combat skill trigger system is implemented.** Extend by adding skills to `skills.json` + handlers in `SkillSystem.js`.
- **Separate game logic from rendering.** Combat math, level-ups, and economy must be importable as pure functions.
- **Don't assume a single campaign.** Current `ACT_CONFIG` in constants.js is a step toward campaign-level config.
- **Difficulty is data-driven.** `difficulty.json` + `DifficultyEngine` provide modifier layers. Wire new systems through this.
- **Decouple combat resolution from animation.** Calculate results first, then play visuals.
- **XP is applied before it is drawn.** `awardScaledXP` applies every battle gain at once and queues plain records: an EXP gauge (`scene._pendingXpGauges`, `ui/xpGaugeModel.js`) and level-up cards (`_pendingLevelUpPopups`). `presentQueuedProgress` (`ui/BattlePresentationCheckpoint.js`; `presentQueuedLevelUps` is an alias) plays each unit's gauge (`ui/XpGaugeController.js`), then its cards, then the prologue's level-up beat, never over a prologue note. Only pending cards make a boundary a recovery; clear both queues together (rewind, fatal, restart). Spec: `docs/specs/exp-bars.md`. A player unit's levels from play (battle XP, Team XP, the arena pass `gainExperience({ guard })`) take the streak guard in `UnitManager.levelUp` (an all-miss level and a second thin level in a row go to the closest miss; flag `unit.lastLevelUpThin`), from the same 8 draws: join levels, enemies and mercenaries roll as ever.
- **Floating combat numbers have one look.** Every number that floats over a unit (a blow, a crit, "No damage", a heal, a drain, a poison, lava or acid tick, a miss, Thorns, a ballista bolt, a Deathburst, the Entity's splash) takes its text, colour, size, depth and motion from `ui/combatNumberStyle.js` (pure) and is drawn by `ui/CombatNumberFloat.js` (`floatCombatNumber`, or `buildCombatNumber` where the flow awaits the number's tween): text through `presentationText`, the spark's Graphics inside `withPresentationRandom`, no emitters, so a float never advances the battle stream; reduced motion is a still hold then a fade (no rise, pop or spark growth). A new float site passes a kind, never its own style (`tests/CombatNumberStyle.test.js`, `tests/CombatNumberFloat.test.js`).
- **HP changes go through `engine/UnitHealth.js`; rendering never changes game state.** `setUnitHP` / `healUnit` / `damageUnit` / `applyCombatHP` keep the rules that ride on HP (HP accessory debt is settled the moment a unit is full or down) whether or not anything is drawn. Scenes and UI never write `currentHP` (`tests/HpWriteBoundary.test.js`); `tests/HealthPresentationInvariance.test.js` resolves the same combat with strikes shown, not shown and bars never drawn and requires identical state. Combat results carry everything that changes HP (Thorns sets `strikerHPAfter`), never the animation. A unit that joins mid-battle (a reinforcement, a raised Skeleton, a risen Zombie) is on the roster with its battle entity id, history beat and par change before anything is drawn; its sprite, banner, fog refresh and arrival band go through `safeBattlePresentation`, so a draw that throws never stops the rest of the wave, raise or rise, nor the enemy phase; a sprite that fails is cleared and a plain marker (faction colour and HP bar) stands in, and a unit nothing could draw is tried again at the next player turn's checkpoint, which asks for a reload if it still fails, but only over a checkpoint that was written (a refused save keeps the save-retry flow's choices and the offer waits for the next write that lands, `noteDurableSave`); a resume and a Vision rewind redraw the roster the same way (each unit still undrawn is tried again once the restored state is saved), and every redraw, sprite or marker, takes the fog's verdict as it is drawn, so the player never plays against an invisible unit (`ui/arrivalGraphic.js`; `tests/ArrivalPresentationFailure.test.js`: every drawing call failing in turn, the harness's arrivals, the real enemy-phase lifecycle).
- **A move is dressed as a walk, never simulated as one** (`ui/WalkCycleController.js`, rules in the pure `ui/walkCycleModel.js`): map sprites have no walk frames, so while a unit crosses its path the idle frames run at a step cadence (about 100 ms a frame at a Normal 80 ms tile, scaled with the step's own time, so Fast doubles it), the sprite hops 1-2 px per tile (a flier glides, an Ice slide glides: no hop, the frame held), and it lands in a small pooled mote puff of the ground it stops on (`puffFamilyFor` reads the knock-back dust's `dustKeyFor`: dust, leaves, splash, mire, snow, sand, stone, ash). BattleScene only calls `_walkCycle().step(unit, { ms, slide })` as each tile's tween is made and `.end(unit, { col, row })` when the move ends (`moveUnit`, `handleCantoClick`, `animateEnemyMove`; `end(unit)` with no tile when cut short or failed: no puff); the controller adds no wait, tween or callback to a move. The tween writes y as an absolute each frame, so the hop is added on `postupdate` and taken back exactly (`appliedY` / `baseY`); `g._walkCycle` pauses the map idle loop on a walking unit, and the rest frame and height are restored on end, release, reset, destroy, stale walk (no step for 3 s) and reduced motion. No hop, cycle or puff under reduced motion or Instant speed (at Instant a player's walked tile, like an enemy's step, is a 1 ms tween: `combatTiming.playerMoveStepDuration`); no puff on low effects, for a flier, or on a tile the player cannot see (`isUnitSeenAt`, so a hidden foe's landing is never shown); the puff's pool is built inside `withPresentationRandom` and its variation is seeded (`createSeededRng`), so Math.random (the battle RNG) is never drawn. Every entry point sits in `safeBattlePresentation`. Tests: `tests/WalkCycleModel.test.js`, `WalkCycleController.test.js`, `WalkCycleBattleWiring.test.js`.
- **Camera shake is seeded, never Phaser's** (`art/combatFx/screenShake.js` pure plan, `ui/ScreenShakeController.js`): Phaser's `camera.shake` draws Math.random every frame, which is the battle RNG, so it stays banned. A shake (`crit`, `boss`, `crash`, `splash`, `stone`; a few px, at most 400 ms) is a whole-pixel offset list from its own seeded RNG, added to the world camera's matrix on `prerender` (scroll, zoom and position are never written, so nothing needs restoring), only when a separate UI camera exists (so the HUD never moves), off under Reduce motion and Instant speed. Callers go through `BattleScene.shakeScreen(kind)` (`safeBattlePresentation`); hooks: `critImpact`, a boss blow on a player unit (`ui/impactFeedback.js`), a stone break, a ram's crash beat (`impact: 'crash'`), the Entity's splash. **Haptics** (`utils/haptics.js` `haptic(kind)`: `@capacitor/haptics` on a native shell whose injected bridge lists the plugin (`nativeCapacitor` + `hasNativePlugin`): its registered interface, imported lazily on the first haptic (importing `@capacitor/core` rewrites `window.Capacitor`, so a browser never loads it), the bridge's `nativePromise` until it lands; every call stateless, a tick a light impact, never `selectionChanged()`; else `navigator.vibrate` (never the plugin's web shim); ticks throttled; never throws; setting `vibration`, shown only where `hapticsSupported()`). Tests: `tests/ScreenShake.test.js`, `tests/Haptics.test.js`.
- **Weather is presentation only** (`ui/WeatherController.js`, pure `art/weatherConfig.js`): rain for Iron Rain, ash for Ashfall, snow on tundra/Rime Night, embers on volcanic maps, motes in castles and the Throne, unlight in the Deep, none in Ember Dusk, Bleached Rite or a scripted battle. It follows the Atmosphere setting (Full; Reduced, the phone default, about a third as many and slower; Off), is off under Reduce motion or without WebGL, uses a fixed pool stepped on its own seeded RNG (never Math.random, never a Phaser emitter) at `UI_DEPTHS.WEATHER` on the world camera, and turns itself off for the battle on a draw failure. Review: `?weather=<kind>` (dev). Tests: `tests/WeatherConfig.test.js`, `tests/WeatherController.test.js`.
- **Map lighting is presentation only** (`art/atmosphereConfig.js`, `art/BattleLightLayer.js`, `art/cloudShadows.js` + `art/CloudShadowLayer.js`, wired by `ui/AtmosphereController.js`): about a quarter of outdoor Act I-III battles fall at night (`resolveTimeOfDay`, hashed from the battle's generation seed, never Math.random; never scripted, a castle, Act IV+ or a run's opening map): the act's night grade (Moonrise, Storm Night, Pale Moon) and the `moonlit` lantern layer, fireflies on a clear night, rain kept on Act II's; 15% each fall at dusk or dawn (the hash's next bands, so no night moved): the act's `_dusk` / `_dawn` grade (Last Light, Red Sky, Vesper / Daybreak, Grey Dawn, Pale Dawn), a thin `dusk` / `dawn` light layer and a static low-sun wash (`art/skyWash.js` + `art/SkyWashLayer.js`: warm glow from the sun's screen corner, cool shade in the far one), fireflies at a clear dusk, rain kept on Act II's. A castle map is lit indoors (`hall` preset by day, its night preset at night): wall sconces on the faces the camera sees (`wallTorchSites`, as drawn, so a portrait board is right) and pillars throwing the nearest sconce's shadow. Daylit Ember Dusk and Bleached Rite outdoors get drifting cloud shadows (a seeded pure plan of time; still under Reduce motion). No vision, fog, AI or difficulty change. Review: `?timeOfDay=night|day|dawn|dusk` (dev); a `?devScene=battle` route is day without it (`devTimeOverride`: its browser specs were written against daylight, and a lit hour's full-screen layers slow CI's software renderer past timing-sensitive specs). Tests: `tests/MapLighting.test.js`, `tests/AtmosphereController.test.js`.
- **Sound effects are composed in code** (`tools/sfx/build.py`, numpy + ffmpeg; `tools/sfx/README.md`): each cue is a seeded function, loudness-matched and self-checked after encoding. The catalog is `utils/sfxConfig.js` (`ESSENTIAL_SFX`, `COMBAT_SFX`, the always-deferred `UI_SFX`, `ALL_SFX`, `SFX_FALLBACKS`: a cue not yet loaded plays what that spot played before); `AudioManager.playSFX` treats `SOFT_SFX` (the menu whooshes `MenuSurface` plays, `sound: false` to opt out) as silent when another sound plays on the same press. After a rebuild run `npm run sync-assets` and `npm run build:audio`. Tests: `tests/SfxCatalog.test.js`, `tests/SfxServiceHooks.test.js`.
- **Previews read what the player knows.** Anything shown before a commit (blue range, path/slide preview, Danger, pinned/inspected reach, Threat Sight) reads `engine/PlayerKnowledge.js` (via `BattleScene.buildUnitPositionMap()` / `buildOccupiedSet(u, { seenOnly: true })`); only execution and the enemy AI see every unit. A staff never counts as damage reach (`ThreatForecast`). `tests/PlayerKnowledgePreviews.test.js` pairs worlds that differ only by a hidden unit. **The Entity's two reaches** (`engine/EntityReach.js`, pure): its blows reach `ENTITY_PRIMARY_ATTACK_RANGE` (3) from its 3x3 body but its weapons say 1-4, so `Combat.canCounter` answers from 4 tiles. `enemyThreatTiles` returns a third set, `counter` (Entity only; distances beyond the strike reach where `canCounter` holds for its equipped weapon, read from the weapon's range, never a literal), and `computeDangerTiles(ctx, { counter: true })` (the display callers: `BattleScene.calculateDangerZone` by default) adds those tiles with `counterThreat: true`, `count` 0, `damageThreat` false. ## Testing
- **Framework:** Vitest (works natively with Vite config and ES modules)
- **Run:** `npm test` (single run) or `npm run test:watch` (live re-runs)
- **CI gates** (`.github/workflows/ci.yml`; run the relevant ones before a PR):
  - `lint`: `npm run format:check`, `npm run lint`
  - `test`: `npm run validate:data`, `check:data-parity`, `check:ui-theme`, `check:sprites`, `check:reference`, `build`, `test:unit`
  - `harness`: `npm run check:threshold-pr-notes`, `test:sim` and `test:harness` (every vitest file in `tests/sim` and `tests/harness`; `test:unit` excludes both), `test:harness:pr`, `sim:fullrun:pr`
  - `e2e`: one job per lane shard of `tests/e2e/lanes.json`, the only list of browser lanes. Run one with `npm run test:e2e:lane -- <lane>` (`npm run test:e2e:lanes` lists them). `npm run check:e2e-lanes` fails when a spec is in no lane and not excluded with a reason, or when a lane names a missing spec. A new spec goes into a lane. Tests run fully parallel (the unit of work is a test, not a file; the release config excepted: its specs serve `dist/` on fixed ports), and a sharded lane is split by measured time, not test count: `tests/e2e/durations.json` (seconds of work per spec) feeds `planShards`; every e2e job logs its specs' times (`tools/e2eDurationReporter.js`, `[e2e durations]`, also the job summary and an `e2e-durations-*` artifact). `node tools/e2eLanes.js plan` shows each shard's estimated work; refresh the numbers with `node tools/e2eLanes.js durations <folder of reports>` when shards drift apart, and raise a lane's `shards` when its shards pass ~16 min of work (about 8 min on CI's two workers per job; a third worker per job was tried and slowed every test into its timeouts). The CI matrix lists the longest shards first, so they leave the runner queue first.
  - **Draft PRs skip `e2e`** (CI's runners are the bottleneck, and the browser lanes are most of their time); marking the PR ready for review runs them. A draft's green check is not a merge signal: merge only after the ready-for-review run is green. Bring `main` into a PR only when it conflicts (each merge re-runs every lane); `main`'s own run catches two PRs that break together.
  - Main's CI run is never cancelled mid-run (pushes waiting behind it collapse to the newest); the TestFlight and Play gates (`tools/releaseGate.js`, `tests/ReleaseGate.test.js`) wait up to 4 hours for the exact commit's newest CI run and accept it for an upload only if it passed with its browser lanes run (a draft's green run is development CI, not release validation), so build the newest main commit.
  - `E2E_PORT=<port>` gives a checkout its own dev server; the default 3000 is reused if something already listens there.
- **Coverage is measured, not counted.** A fault-injection pilot (Sep 2026) found about half of realistic injected bugs survive the whole unit suite. Gaps, rules and the delete/rewrite procedure: `docs/specs/compression-plan-2026-09-25.md`.
- **Residual gap:** BattleScene orchestration logic is undertested relative to its complexity. `tests/harness/HeadlessBattle` mirrors the scene's state machine (Canto off, no async presentation, no resume), so a green harness run does not prove the production action lifecycle. Operations move out of the mirror as they are isolated: post-combat effects run from `engine/PostCombatEffects.js` (a generator the scene drives with presentation and the harness drives without), timed weapon-art buffs from `engine/TimedWeaponArtBuffs.js`, battle stat deltas from `engine/BattleStatDeltas.js`, battle XP (who earns what, the battle's multipliers, the gain and its skills) from `engine/BattleXp.js`, the Necromancer's raising and crumbling from `engine/Necromancy.js`, the Vigil's words and summons from `engine/Vigil.js`, Deathburst from `engine/Deathburst.js` (`deathburst`: a generator yielding each blow after its HP change so the scene presents it and removes a fallen victim, with the burster's credit, before the next; the harness's `_removeUnit` drives it with `runDeathburstSync` and, as the scene, never removes a unit already off its roster; `tests/DeathburstStep.test.js`), blessing combat bonuses (Keen Eye, Hold the Line, the act Hit price) from `engine/BlessingCombatMods.js`, the Entity's splash from `engine/EntitySystem.js` (`entitySplash`: a generator that applies each hit through `damageUnitDetailed` with the banner and yields it before reading the next tile, so the scene's presentation and removals interleave with its battle-stream draws exactly as before; the harness drives it with `runEntitySplashSync` in `_executeEnemyCombat`, so harness finales splash too; the count is `entitySplashCountFor(battleConfig)`, `entitySplashCount` ?? `ENTITY_SPLASH_COUNT` clamped 0..4, and `rollSplashTiles` takes the same draws at any count; `tests/EntitySplashStep.test.js`). When you extract another, delete the harness copy; don't keep both.
- **Writing tests:**
  - List the realistic ways a change can fail first; each test should catch one of them.
  - Assert outcomes (player-visible or persisted state, RNG cursor), not internal call order.
  - Derive expected values independently, never by re-running the code under test.
  - Before a refactor, pin current behaviour with tests that pass before and after; a bug fix gets a test that fails before it.
  - Prove a new test can fail by planting the bug once.
  - Every `tests/e2e` spec must belong to a CI lane or have a stated exclusion (`tests/e2e/lanes.json`, enforced by `npm run check:e2e-lanes`).
  - In browser specs, wait on state, never on time: a sleep that "usually" suffices rots under load (see `padTap` in `tests/e2e/helpers.js` for driving the gamepad reader).
- **Pattern:** Tests import pure engine modules directly + load JSON from `data/` via `tests/testData.js`. No Phaser needed.

## Key Design Principles
- **Data-driven:** All content in JSON. Never hardcode stats, classes, or weapons.
- **Testable phases:** Each build phase should produce something playable/verifiable.
- **Classic FE feel:** Player Phase / Enemy Phase turns, weapon triangle matters, positioning matters, growth rates create unique units.
- **Roguelike tension:** Permadeath (run ends on Edric's defeat only — other lords can fall), meaningful loot choices, randomized recruits, gold scarcity, deploy selection.

## God Objects & Decomposition Strategy

Several files have grown large enough to require active management. When adding features, prefer extracting to a new controller/module over expanding these files further.

### Critical (actively decompose)
- **BattleScene.js (~12,100 lines)** — 13 controllers extracted (5 original + PostCombatController, TransitionRecoveryController, LootFlowController, WeaponArtController, InputController, HealController, PromotionController, PrologueController). **Rule: never add new rendering or multi-step flows inline. Extract a controller with `create(scene)` / `destroy()` pattern.**

### Large (watch for growth)
- **NodeMapScene.js (~2,700 lines)** — ChurchController/ShopController now own lifecycle and persistence only; ChurchMenu/ShopMenu and ArenaMenu are the sole service renderers. Do not restore headless canvas branches for tests—use rendering-only test adapters and real engine commands.
- **RunManager.js (~6,700 lines)** — The run-start blessing effects are a handler table (`engine/RunStartBlessingEffects.js`, pinned by `tests/BlessingEffectFingerprints.test.js`); storage and migrations (`fromJSON`, the `migrate*` statics) are the next candidate.
- **RosterOverlay.js (~2,780 lines)** — Trade state machine extracted to RosterTradeController (state stays on the overlay; methods are delegating shims).

### Guardrails
Line budgets (`tests/FileSizeBudget.test.js`: these files only shrink; lower a budget when a PR frees room), no `src/engine/` import of `src/ui/`, `src/scenes/` or Phaser (`eslint.config.js`), and no new static import cycle (`tests/ImportCycles.test.js` against `tools/importCycleBaseline.json`; `npm run check:cycles -- --write` after breaking one). A new rule is a pure function in `src/engine/` that the scene and the harness both import, never a BattleScene method the harness copies.

### Extraction pattern
```js
export default class NewController {
  constructor(scene, options) { /* store refs, no rendering */ }
  create() { /* build UI, bind input */ }
  destroy() { /* remove all Phaser objects, unbind input */ }
}
// In BattleScene: this.newCtrl = new NewController(this, opts); this.newCtrl.create();
```

## UI Polish Guidelines

Text overflow, clipping, and layout issues are a recurring problem. Follow these rules for all UI work:

### Common pitfalls
- **Text overfill:** Long class/weapon/skill names overflow containers. Always test with longest possible strings.
- **Overlay stacking:** Use `uiDepths.js` constants, not magic numbers.
- **Font size:** 9px `'Press Start 2P'` has wide characters. Budget ~8px per character width.
- **Dynamic lists:** Handle 0 items (empty state) and max items (scroll bounds) gracefully.

### Prevention checklist (for any UI change)
1. Test with maximum-length names/values for all text fields
2. Verify on 640x480 base resolution (the design target)
3. Check that overlay depth uses `uiDepths.js` constants
4. Confirm ESC/close handlers don't leak (use `escPriority.js` for stacking)
5. For scrollable lists: test empty state, 1 item, and overflow count
